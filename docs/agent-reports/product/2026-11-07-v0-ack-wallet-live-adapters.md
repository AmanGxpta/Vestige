### Deviations and gaps found while integrating

1. **C1 canonicalizer accepts sparse arrays.** At `agent/identity@1b502e6`, `canonicalize([1,,2])` returns `"[1,,2]"`, which is not valid JSON. CONTRACTS says sparse arrays are invalid. C2 rejects them. The C1 output is recorded in `c1-vectors.json` (`sparse-array`). This needs a C1 fix, not a contract change. It cannot be triggered through `buildTermsDoc`, which rebuilds the document from validated fields, but the shared vector suite should agree.
2. **C1 has no handler for these yet:**
   - `DELETE /api/identity/auth/session`: C2 drops the token locally and the server token lives until expiry.
   - `GET /api/identity/ventures`: C2 shows BLOCKED.
   - `POST …/listing`: C2 shows BLOCKED.

   All are contract routes owed by C1.
3. **C1 `signingPayload` requires `nonce` and `expiry`.** The contract calls them optional hints. C2 always sends bounded values (`expiry` = now + 30 min), so this is compatible.
4. **Founders-only GET refuses a not-yet-joined founder.** This is correct per contract. The join page therefore does not depend on it: the invite link carries the code and the ENS name in the **URL fragment**, which is never sent to a server or in Referer headers. The name is labelled "from the invite link" until the API confirms it.
5. **X has not shipped HTTP handlers or published ABI JSON or a manifest.** All treasury routes resolve to BLOCKED. Funding checks the route and the treasury **before** asking for any signature.

## 2. What changed (owned paths only)

- **Agreement:** `src/modules/ui/agreement/terms.ts` contains C1's NFC/UTF-16-sorted restricted canonical JSON, the `buildTermsDoc` mirror (same limits, trimming, lowercase wallets, sort, fixed disclaimer) and the EIP-712 domain and type. `c1-vectors.json` holds the vectors generated from C1's code. The terms page is rebuilt around per-founder role, contribution, ownership % (stored as bps) and vesting, plus decision rule, effective date, notes, inline validation and a live preview hash.
- **Wallet:** `src/modules/ui/wallet/eip1193.ts` handles discovery, connect, explicit `switchChain` (with 4902 → `wallet_addEthereumChain` for Whitechain 0x752), `signTypedData`, and `signMessage`. `signTypedData` refuses rather than switching when the wallet is on the wrong chain or account. The header wallet control shows the network, offers explicit "Switch to …" buttons, and has sign in and sign out. The signature prompt shows the target network and requires a **Switch** click before **Sign** appears.
- **Adapter seam:** pages pass a plain-language prompt, and the adapter supplies the exact typed data through a `TypedDataSigner`. Added `createInvite`, `requestWorld`, `setListing`, `signIn` and `signOut`.
- **Live adapter (`live-adapter.ts`):** all C1 routes are mapped from C1's handlers. Before the wallet is asked to sign, it checks:
  - the World `action` and `signal`;
  - the FoundingTerms domain, venture, version and docHash against what the founder reviewed;
  - the EIP-3009 domain against the manifest and the approved USDT;
  - that the SafeTx targets this Safe on 1874 as a plain USDT transfer.
- **World (live):** `components/WorldIdKitPrompt.tsx` uses `@worldcoin/idkit-core@4.6.0` (the same version as C1) with C1's server-pinned, RP-signed parameters. It shows a QR code plus a copyable connector link, which the World ID Simulator accepts on staging, and a staging banner.
- **Public page:** reads ENS `vestige.ventureId`, the Guard binding, the code hashes and the manifest. Verdict kinds: an `invariant` failure gives NOT_ACTIVE; a `consistency` failure or missing data gives UNVERIFIED.
- **Funding:** the funder page is now `/funder/<ensName>`. It uses the public summary only and resolves the Safe from ENS before allowing a deposit.
- **DEV MOCK:** reworked to the same seam, with mock typed data in the real shapes. It stays visibly labelled and is refused in production.

## 7. Honest demo path (recordable with staging World evidence, no real participants)

Every step states its claim class on screen.

1. **Public page first (VERIFIED_ON_CHAIN, read-only).**
   - Open `/v/<venture>.vestige.eth` on the live build.
   - With H's ENS name and X's manifest: ENS → `vestige.ventureId` → Safe, Guard binding, code hashes, owners, threshold 2, no modules, `isSeat` → USDT transfers from `deploymentBlock`.
   - Without them, show the page refusing to say ACTIVE: "No treasury linked" / "manifest not configured". That is the honest state today.
2. **Founder flow on the live build with C1 deployed, World `staging` (TESTED_IN_SIMULATOR).**
   - Two browser profiles (Founder A, Founder B), each with its own MetaMask EOA.
   - Connect → Sign in (free signature) → create venture → create invite → B opens the fragment link → join.
   - Verify: the IDKit modal shows the "World staging — TESTED IN SIMULATOR" banner. Paste the connector link into the World ID Simulator.
   - Use the **same simulator identity** for both seats to show the duplicate-human refusal ("This human already holds a seat in …"). Then use a different identity for B.
   - Seats show `HUMAN_VERIFIED` + **TESTED IN SIMULATOR**, never production uniqueness.
3. **Terms (SIGNED, off-chain).**
   - Draft the terms and save. The preview hash equals C1's stored hash.
   - Signing shows the explicit **Switch to Ethereum Sepolia** step if the wallet is on Whitechain.
   - Both sign. Edit one word: signatures reset. Re-sign.
4. **Treasury (only with X's deployed handlers and H-approved deploy).**
   - The status stays "Confirming…" until chain read-back, then the public page re-reads it.
   - If X is not live: show the BLOCKED notice. Do not cut to the mock.
5. **1-of-2 rejection.** Show the relayer refusal (simulation), then the **mined GS020 receipt** read from Whitechain (H-C2-05c). If that hash does not exist yet, the card says "Awaiting the real failed transaction"; never fake it.
6. **Optional UX walk-through in DEV MOCK (MOCK_ONLY).** Use only to show the screens before the backends exist, with the DEV MOCK banner and MOCK tags visible throughout. Never present it as evidence.
